## Executive Summary

## Findings

### CRITICAL-1: Tenant Isolation Bypass via X-Store-ID Header

**Severity:** CRITICAL  
**Issue:** FR-1 states "X-Store-ID header accepted only for platform_admin role" and "Middleware rejects non-admin requests with X-Store-ID header via 403." However, the current `TenantMiddleware` implementation (`core/middleware.py:58-79`) accepts X-Store-ID from **any** request without checking the JWT role claim. A store owner with a valid JWT for Store A can send `X-Store-ID: <Store-B-UUID>` and access Store B data.

**Evidence:**  
- `TenantMiddleware.process_request()` at line 59-79: No JWT decoding or role check
- Architecture review (`review-architecture.md`) already flagged this as "C-1"
- Addendum A1 describes the fix but it is NOT implemented

**Recommended Fix:**  
1. Decode the JWT in `TenantMiddleware` when `X-Store-ID` header is present
2. Extract the `role` claim from JWT
3. If `role != platform_admin`, return 403 immediately
4. Add cross-tenant isolation test (`pytest -m cross_tenant`) to CI before launch

**Launch Blocker:** YES — this is a P0 fix

### HIGH-1: No Rate Limiting on M-Pesa Callback Endpoint

**Severity:** HIGH  
**Issue:** FR-11 mentions "Callback flood (DoS) handled via rate limiting" but the `MpesaCallbackView` (`apps/payment/views.py:98-121`) has no rate limiting applied. The endpoint uses `AllowAny` and `authentication_classes=[]`, making it a DDoS surface.

**Evidence:**  
- `MpesaCallbackView` has no `throttle_classes` attribute
- No Nginx-level rate limiting configured for `/api/v1/payments/mpesa-callback/`
- Project context (`project-context.md:336`) explicitly states: "/api/v1/payments/mpesa-callback/ must be rate-limited at both Nginx level AND DRF throttle level"

**Recommended Fix:**  
1. Add `throttle_classes = [AnonRateThrottle]` to `MpesaCallbackView`
2. Configure `DEFAULT_THROTTLE_RATES` for anonymous users (e.g., `anon: '100/hour'`)
3. Add Nginx rate limiting for the callback path in production
4. Consider IP whitelist for Safaricom/Daraja callback IPs (if published)

### HIGH-2: JWT Secret Key Rotation Not Addressed

**Severity:** HIGH  
**Issue:** The PRD does not address JWT secret key rotation. `DJANGO_SECRET_KEY` is auto-generated by Render (`render.yaml:17`) but there's no rotation mechanism. If the key is compromised, all active JWTs become invalid or forgeable.

**Evidence:**  
- `render.yaml:16-17`: `DJANGO_SECRET_KEY` generated once at deployment
- No mention of key rotation in PRD, epics, or architecture
- `SIMPLE_JWT` uses `HS256` (default) which signs with `DJANGO_SECRET_KEY`

**Recommended Fix:**  
1. Add FR for JWT secret rotation (quarterly recommended)
2. Document rotation procedure: generate new key → update env var → redeploy
3. Consider dual-key support during rotation window (old + new key valid)
4. Add key rotation to platform admin dashboard ( Epic 8)

### HIGH-3: Missing Data Subject Access Request (DSAR) Endpoint

**Severity:** HIGH  
**Issue:** Kenya DPA 2019 §26 grants data subjects the right to access their personal data. The PRD mentions "Data portability: GET /api/v1/analytics/export/csv/" for merchants but no endpoint exists for customers to request their data.

**Evidence:**  
- `OWASP DPA compliance checklist.md` mentions "Data portability" but only for merchants
- No FR for customer DSAR endpoint
- DPA 2019 §26: "A data subject shall have the right to obtain from the data controller confirmation as to whether or not personal data concerning the data subject is being processed"

**Recommended Fix:**  
1. Add FR: Customer DSAR endpoint (POST /api/v1/hub/dsar-request/)
2. Return: orders, payments, phone/email within 30 days
3. Log DSAR requests in `AdminPIIAccessLog` for audit trail
4. Add DSAR handling to incident response runbook

### HIGH-4: No Consent Management for Customer Data Collection

**Severity:** HIGH  
**Issue:** The PRD mentions "Customers provide explicit consent during checkout (required checkbox in storefront)" in the DPA compliance checklist, but no FR defines the consent collection, storage, or withdrawal mechanism.

**Evidence:**  
- `OWASP DPA compliance checklist.md:84`: mentions consent checkbox
- No model for storing consent records
- No endpoint for consent withdrawal
- DPA 2019 §30: "Consent shall be given by a clear affirmative action"

**Recommended Fix:**  
1. Add FR: Consent model (customer_id, store_id, consent_type, granted_at, withdrawn_at)
2. Add FR: Consent withdrawal endpoint (DELETE /api/v1/hub/consent/{type}/)
3. Anonymize customer data upon consent withdrawal
4. Log consent changes in audit trail

### MEDIUM-1: No API Versioning Strategy

**Severity:** MEDIUM  
**Issue:** The PRD defines endpoints as `/api/v1/` but no versioning strategy is documented. Breaking changes in production will require client coordination without versioning.

**Evidence:**  
- All endpoints use `/api/v1/` prefix
- No mention of versioning strategy in architecture
- No deprecation policy

**Recommended Fix:**  
1. Document API versioning strategy (URL path versioning is already in place)
2. Add FR: API version deprecation policy (6-month notice)
3. Add `Sunset` header support for deprecated versions
4. Document versioning in OpenAPI schema

---

### MEDIUM-2: No Request Size Limits

**Severity:** MEDIUM  
**Issue:** No mention of request body size limits. Large payloads could cause memory exhaustion or denial of service.

**Evidence:**  
- No `DATA_UPLOAD_MAX_MEMORY_SIZE` in Django settings
- No Nginx `client_max_body_size` configuration documented
- File uploads (logo, product images) have size limits but general API does not

**Recommended Fix:**  
1. Add `DATA_UPLOAD_MAX_MEMORY_SIZE = 2621440` (2.5MB) to production settings
2. Add `FILE_UPLOAD_MAX_MEMORY_SIZE = 5242880` (5MB) for file uploads
3. Configure Nginx `client_max_body_size 5m;`
4. Document in architecture.md

---

### MEDIUM-3: No Audit Trail for Admin Actions

**Severity:** MEDIUM  
**Issue:** `AdminPIIAccessLog` tracks PII access but no audit trail exists for admin actions (store creation, plan changes, subscription modifications).

**Evidence:**  
- `AdminPIIAccessLog` only logs PII access, not admin actions
- No model for admin action audit log
- Platform admin can create/modify stores without audit trail

**Recommended Fix:**  
1. Add FR: `AdminActionLog(user, action, target_store, details, timestamp)` model
2. Log: store creation, plan changes, subscription modifications, store suspension
3. Make log immutable (INSERT-only, no updates/deletes)
4. Retain for 12 months per Kenya DPA 2019

### MEDIUM-4: No Password Complexity Requirements

**Severity:** MEDIUM  
**Issue:** FR-2 mentions "System generates temporary password" but no password complexity requirements are defined. Django's default `AUTH_PASSWORD_VALIDATORS` may not be sufficient.

**Evidence:**  
- `FR-2`: "System generates temporary password, sends onboarding email"
- No mention of password policy in PRD
- `OWASP DPA compliance checklist.md:51`: mentions "Password policy: Django's built-in AUTH_PASSWORD_VALIDATORS applied" but validators not configured

**Recommended Fix:**  
1. Add FR: Password complexity requirements (min 12 chars, mixed case, numbers, symbols)
2. Configure `AUTH_PASSWORD_VALIDATORS` in `base.py`:
   - `MinimumLengthValidator(12)`
   - `CommonPasswordValidator`
   - `NumericPasswordValidator`
3. Add password strength indicator to admin dashboard
4. Enforce password change on first login after provisioning

---

### MEDIUM-5: No Session Timeout Configuration

**Severity:** MEDIUM  
**Issue:** JWT access tokens expire in 15 minutes, but no session timeout is configured for Django admin sessions or remember-me functionality.

**Evidence:**  
- `SIMPLE_JWT`: 15-minute access token, 7-day refresh token
- No `SESSION_COOKIE_AGE` configured in production settings
- Django admin session defaults to 2 weeks

**Recommended Fix:**  
1. Add `SESSION_COOKIE_AGE = 3600` (1 hour) to production settings
2. Add `SESSION_EXPIRE_AT_BROWSER_CLOSE = True`
3. Document session management in architecture.md
4. Consider sliding window for refresh tokens

---

### LOW-1: No CSRF Protection for Webhook Endpoints

**Severity:** LOW  
**Issue:** Webhook endpoints (`MpesaCallbackView`, `StripeWebhookView`) use `AllowAny` and `authentication_classes=[]`, bypassing CSRF protection. This is acceptable for webhooks but should be documented.

**Evidence:**  
- `MpesaCallbackView`: `permission_classes = [AllowAny]`
- `StripeWebhookView`: `permission_classes = [AllowAny]`
- CSRF protection disabled for these endpoints

**Recommended Fix:**  
1. Document in architecture.md that webhook endpoints are CSRF-exempt by design
2. Ensure HMAC/signature verification is mandatory (already implemented)
3. Add comment in code explaining CSRF bypass rationale

---

### LOW-2: No CORS Pre-flight Caching

**Severity:** LOW  
**Issue:** CORS headers are set but no `Access-Control-Max-Age` header is configured, causing pre-flight requests on every cross-origin call.

**Evidence:**  
- `CORS_ALLOWED_ORIGINS` configured in production
- No `CORS_PREFLIGHT_MAX_AGE` setting
- Browser will send OPTIONS request for every cross-origin call

**Recommended Fix:**  
1. Add `CORS_PREFLIGHT_MAX_AGE = 86400` (24 hours) to production settings
2. Reduce pre-flight requests for better performance
3. Document in architecture.md

---

### LOW-3: No Security.txt File

**Severity:** LOW  
**Issue:** No `/.well-known/security.txt` file exists for responsible disclosure. Security researchers have no way to report vulnerabilities.

**Evidence:**  
- No `security.txt` in codebase
- No mention of vulnerability disclosure process
- OWASP recommends security.txt

**Recommended Fix:**  
1. Create `/.well-known/security.txt` with:
   - Contact: `security@joat.com`
   - Encryption: PGP key
   - Policy: responsible disclosure
   - Expires: 1 year
2. Add to static files or Nginx config
3. Document in README.md

## Threats Not Addressed

### T1: Insider Threat (Platform Admin)

**Risk:** Platform admin can access any store's data via X-Store-ID header (by design). No monitoring or alerting for unusual access patterns.

**Mitigation:**  
- Log all platform admin cross-store access in `AdminPIIAccessLog`
- Add alerting for >10 different store accesses per hour
- Quarterly access review

### T2: M-Pesa Callback Spoofing

**Risk:** If `MPESA_WEBHOOK_SECRET` is compromised, attacker can forge payment confirmations.

**Mitigation:**  
- Rotate `MPESA_WEBHOOK_SECRET` quarterly
- Log callback source IPs (if Safaricom publishes IP ranges)
- Add transaction amount validation against expected amount

### T3: QR Code Forgery

**Risk:** If `HMAC_QR_SECRET` is compromised, attacker can forge QR codes for any store/table.

**Mitigation:**  
- Rotate `HMAC_QR_SECRET` quarterly
- Add 24-hour expiry to QR tokens (mentioned in architecture review L-2)
- Log QR scan attempts for anomaly detection

### T4: Subscription Bypass

**Risk:** Store owner could manipulate subscription status to access features without payment.

**Mitigation:**  
- Subscription status managed exclusively by platform admin
- Add integrity check: subscription status changes require platform admin JWT
- Log all subscription modifications

### T5: Data Residency Violation

**Risk:** `render.yaml:6` deploys to `region: oregon` (US), but Kenya DPA 2019 requires Kenya/EAC hosting.

**Mitigation:**  
- Change `region: oregware` to `region: frankfurt` (closest to Kenya on Render)
- Document data residency requirement in architecture.md
- Add compliance check: verify hosting region in pre-launch checklist

## Positive Findings

1. **HMAC Webhook Verification** — Daraja callbacks are properly HMAC-verified before processing
2. **PII Scrubbing** — structlog processor masks phone/email in all log output
3. **Audit Logging** — `AdminPIIAccessLog` tracks PII access by platform admins
4. **Tenant Isolation Architecture** — `TenantModel` + `TenantQuerySet` + `TenantMiddleware` pattern is sound (implementation gap noted)
5. **Rate Limiting** — `StorePlanRateThrottle` reads limits from subscription plan
6. **Security Headers** — `SecurityHeadersMiddleware` adds OWASP-recommended headers
7. **Request Correlation** — `RequestIDMiddleware` provides request tracing

## Conclusion

The PRD has a solid security foundation but requires immediate attention to the **X-Store-ID tenant isolation bypass** (CRITICAL-1) before any production deployment. The missing rate limiting on payment webhooks (HIGH-1) is also a launch blocker.

Address all P0 and P1 items before Sprint 1 begins. P2 items should be addressed within the first month. P3 items can be addressed in the first quarter.

**Security Verdict:** NOT READY FOR PRODUCTION until CRITICAL-1 and HIGH-1 are resolved.
